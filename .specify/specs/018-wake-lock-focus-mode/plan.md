# Implementation Plan: Screen Wake Lock in Focus Mode

**Branch**: `018-wake-lock-focus-mode` | **Date**: 2026-07-31 | **Spec**: [spec.md](spec.md)

## Summary

Hardening pass on an already-shipped capability. Focus mode already acquires a screen wake lock on open and releases it on close (commit `b9b1897`), and the `@vueuse/core` composable behind it already handles re-acquisition on visibility change and feature detection. Three defects remain: the acquire/release calls are unguarded, so a refused request becomes an unhandled promise rejection; `request()` is called with no argument, which silently no-ops when focus mode opens while the tab is hidden; and a voice-over setup failure aborts `onMounted` before the wake lock is ever requested. A fourth gap is observability — `isSupported` and `isActive` are wired up but never rendered, so nobody can tell whether the lock is held.

All four are fixed in **one file**, `src/components/builds/FocusMode.vue`: guard both calls, pass `"screen"` explicitly, hoist acquisition above the voice-over `await`, and surface `isActive` as an indicator in the existing control row. No new files, no new dependency, no backend, no schema.

## Implementation Design

All line references are against the current state of `src/components/builds/FocusMode.vue`.

### 1. Acquire explicitly, guarded, and early (FR-006, FR-008, and the hidden-tab edge case)

Current `onMounted` tail:

```js
//init speak
await initTextToSpeech();
if (audio.value) {
  stop();
  if (!autoplaySupported.value) speak(currentStep.value, announceVillagers.value);
}

//keep screen awake
await request();          // ← line 371, last statement, unguarded
```

Three defects in those two statements, all fixed by one move:

```js
//keep screen awake — must not depend on, or be blocked by, voice-over setup
try {
  await request("screen");
} catch {
  // Wake lock refused (battery saver, page not fully active). Degrade silently.
}

//init speak
await initTextToSpeech();
if (audio.value) {
  stop();
  if (!autoplaySupported.value) speak(currentStep.value, announceVillagers.value);
}
```

- **Guarded** — an unguarded rejection in an `async` `onMounted` callback escapes as an unhandled promise rejection. Refusal is a realistic outcome on the battery-powered phones this feature targets, not a theoretical one ([research.md](research.md) R4). Satisfies FR-006 and FR-009.
- **`"screen"` passed explicitly** — with no argument, the composable's hidden-document branch stores `requestedType = undefined`, and its re-acquire watcher guards on that value being truthy. The lock would then never be acquired for that session. Fixes the "opened while hidden" edge case ([research.md](research.md) R3).
- **Hoisted above `initTextToSpeech()`** — today a voice-over failure aborts the hook before the wake lock is requested. Ordering alone satisfies FR-008 in both directions, with no extra try/catch and no restructuring.

### 2. Guard the release (FR-007)

```js
onBeforeUnmount(() => {
  clearTimer();
  stop();
  release().catch(() => {});   // ← was: release()
});
```

`onBeforeUnmount` is synchronous, so the promise cannot be awaited — a rejection would escape unhandled. `.catch(() => {})` is the correct shape here rather than `try`/`await`.

The explicit `release()` call is **load-bearing and must not be removed**: `useWakeLock` registers no scope-dispose cleanup, so the sentinel outlives the component without it ([research.md](research.md) R2). This is what upholds FR-003 and FR-010.

### 3. Surface the state (FR-013, FR-012)

`isSupported` and `isActive` are already destructured at line 319; `isSupported` is already returned to the template at line 594 but never rendered, and `isActive` is not returned at all. Add `isActive` to the returned object and render both.

New block in the control row, inserted after the villager-announcement tooltip (line 258) and before the Next-step tooltip (line 259):

```html
<v-tooltip location="top">
  <span :style="{ color: $vuetify.theme.current.colors.primary }">
    {{ isActive ? "Screen is being kept on" : "Screen may dim" }}
  </span>
  <template v-slot:activator="{ props }">
    <v-icon
      v-if="isSupported"
      v-bind="props"
      color="accent"
      class="ma-2"
      :icon="isActive ? 'mdi-sleep-off' : 'mdi-sleep'"
    ></v-icon>
  </template>
</v-tooltip>
```

- **`v-icon`, not `v-btn`** — the indicator is non-interactive by design. There is no manual off switch (closing focus mode is how you stop it), so a button would imply an action that does not exist.
- **`v-if="isSupported"`** — hidden entirely where wake lock is unavailable, matching how every other conditional control in this row behaves (`v-if="autoplaySupported"`, `v-if="audio"`). A permanently-dead icon is clutter, and showing nothing cannot mislead. Satisfies FR-013's second clause.
- **Driven by `isActive`, not by "we called request()"** — `isActive` is `!!sentinel && documentVisibility === "visible"`, so it reports *actually holding*, which is what the player needs to know.

This closes FR-012 by *using* the dead state rather than deleting it, and gives the manual tester the only in-page signal that distinguishes User Story 1 from User Story 3 — every quickstart scenario depends on it.
