## Notes

**Caveat on "no implementation details"** — carried over from `020`. This spec names specific
files, composables, Vuetify components and colour values, which a pure spec normally would not.
That is deliberate: six treatments were mocked and rejected before this shape was chosen, and the
resolved values live in [design-input.md](../design-input.md). Losing them would waste the design
work. The user-facing requirements (US1–US4, SC-001–SC-005) remain testable independently of them.

**Restructuring applied to the dropped handoff package**:

- `README.md` → `design-handoff-README.md` and `tasks.md` → `tasks-handoff-draft.md`, matching the
  `020` convention. The draft task list predates `/speckit-plan`; `tasks.md` will be regenerated by
  `/speckit-tasks` once the plan exists.
- Added **Key Entities** (economy series, coverage, last stated moment, open-state preference).
- Added **Assumptions** (A-1..A-7), absorbing the handoff's NC-3 as a resolved decision rather than
  an open question — inheriting the villager-parser defects is a deliberate consistency choice, not
  something to ask about.
- Converted the handoff's NC-1 and NC-2 into inline `[NEEDS CLARIFICATION]` markers on the
  requirements they actually constrain (FR-018, FR-006), so `/speckit-clarify` lands them in the
  right place.

**Clarify session 2026-08-05 — 4 questions, all answered** (recorded in the spec's Clarifications
section):

1. **Preference reach → FR-018**: device-local, stored the way the theme choice already is.
   Identical signed-in and signed-out. The app has no account-bound preference storage today, and
   a Firestore read per build page load for a chevron's state is the wrong trade at this read
   volume.
2. **Coverage gate → FR-006**: two-part — **≥50 % of steps stated AND ≥4 stated steps**. The ratio
   catches prose-heavy builds, the floor catches short builds where a passing ratio still yields a
   three-point chart. Constants validated offline against a real-build sample (no analytics exist
   in the app, so runtime instrumentation was never an option) — A-8.
3. **SC-005 → demoted.** The silhouette read no longer gates the feature; it lives under Success
   Criteria > Design Notes as a non-blocking conviction. *Accepted consequence*: nothing in the
   acceptance path re-tests the shape read on real builds, so a weaker-than-mocked result would
   surface after ship. Recorded in the spec rather than argued.
4. **Plot accessibility → FR-021**: `aria-hidden`, not focusable, treated as a visual restatement
   of the build order table below it. *Accepted consequence*: the shape reading is not conveyed
   non-visually.

**Follow-on effects applied**: SC-002's fixture set grew from five builds to six (added
short-build-under-floor); US3 gained an acceptance scenario for the step floor; assumption A-8
added for the offline tuning of the gate constants.

## Post-plan corrections — 2026-08-05

Phase 0 probing of `timingsHelper.js` invalidated three statements. All applied to the spec:

1. **FR-006 split.** `getTimings()` returns `null` for any build whose trailing steps are unstamped
   — verified empirically, not inferred. Gating on it would have hidden the feature on exactly the
   shape the faded tail was designed for. FR-006 now defines per-step time resolution; **FR-006a**
   carries the coverage gate.
2. **US3 scenario 3 was factually wrong** — it claimed the whole card is absent when `getTimings`
   returns `null`. It is not: `getAgeTimings` survives that by reading each boundary's own
   timestamp. Rewritten to assert *no plottable points*.
3. **SC-006 widened** to five files (`villagerAggregator.js` must export its parser), **SC-002**
   grew to seven fixtures (added trailing-unstamped and no-timestamps-at-all).

**Explicitly not relaxed**: `getTimings()` keeps its all-or-nothing contract and `timingsHelper.js`
stays byte-identical — Focus mode gates autoplay on it, and autoplay is binary. New **SC-007** and
**A-9** pin this so nobody "fixes" the helper and silently hands autoplay unplayable builds.

All checklist items still pass. Spec is ready for `/speckit-tasks`.
